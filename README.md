# 中文接口文档编写

早期我让 Codex 写接口文档，它能写一大堆背景和字段说明。我从头读到尾，准备动手对接了，还是得回去翻代码。拿“查询批次处理结果”这个接口举例。

## 以前的写法（简化示意）

> **查询批次处理结果**  
> 根据批次编号查询数据处理情况。请求参数包括批次编号、页码和每页条数。查询成功后返回处理结果，如有异常，请根据错误信息处理。

我读完最想问的是：批次编号从哪拿？我一次推了几十条，怎么知道哪条写进去了？如果还在处理，我该再查一次，还是把数据再传一遍？

后来我翻了许多接口规范，把自己觉得好用的写法整理成了 `api-docs-zh`。现在让 Codex 按项目代码或第三方协议写中文 Markdown 文档，我希望接手的人能像下面这样，一步一步走完这次调用。

## 现在的写法：查询批次处理结果

**1. 什么时候查**

医院向平台推送一批记录后，用 `POST /open-api/chronic/v1/batches/result` 查询这一批的处理进度和逐条结果。

**2. 请求怎么填**

| 请求体字段 | 取值 |
| --- | --- |
| `batch_id` | 填刚才推送响应里的 `data.batch_id`。如果推送超时，填原推送请求里的 `batch_id`。 |
| `page_no` | 首页填 `1`。 |
| `page_size` | 每页 1～500 条，本例取 100。 |

例如，刚推送的机构批次编号是 `ORG-20261120-001`，查询请求体就这样填：

```json
{
  "batch_id": "ORG-20261120-001",
  "page_no": 1,
  "page_size": 100
}
```

**3. 收到响应后做什么**

| 收到的结果 | 下一步 |
| --- | --- |
| HTTP `200`，响应体 `code = 202` | 平台还在处理。保留批次号，稍后再查同一批。 |
| HTTP `200`，响应体 `code = 0` | 首轮处理已结束。遍历 `data.results[]`，用每项的 `item_key` 对应原推送记录，逐条看 `status_code`。 |

**4. 怎么处理其中一条记录**

假设推送时给某家医院的机构记录填了 `item_key = org-001`。在查询结果里找到 `item_key` 同为 `org-001` 的那一项：

- `status_code = APPLIED`：这家医院的机构记录已写入。
- `status_code = REJECTED`：读这一项的 `errors[].field` 和 `errors[].message`，按提示改正字段，用新的 `batch_id` 重传。机构编码沿用原值。
