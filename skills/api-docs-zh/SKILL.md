# 中文接口文档编写

面向第一次接手的联调人员写 Markdown。让读者能构造第一笔请求、判断业务结果，并取得下一步需要的数据。

## 先还原一笔调用

- 在项目内先读工作区约定和已有接口文档。自有接口从对外入口追到返回：核对路由前缀、方法、参数位置、必要请求头和鉴权，再查校验及其分组、业务分支、异常映射、返回封装和序列化。按对端实际收到的字段名、类型与层级写。数据库非空、类属性存在、单次抓包都有各自的适用范围，不能单独证明对外契约。
- 第三方接口从用户指定的协议版本取数，同时读公共报文、具体交易和关联交易。标准交易与本地适配接口各自标出调用边界。代码与规范有差异时列出具体字段、双方行为以及对联调的影响。先确认会改变请求构造或结果判断的缺口，能确定的部分照常整理。
- 沿一条成功链追到下一步，再查实际失败分支。区分传输成功与业务成功。原文只提供错误字段时，写明从哪里读取；仅在有依据时给出错误触发条件、固定文案、错误码、幂等保证、重试或补偿步骤。

## 按对接方的调用顺序写

单个接口依次设置「接口说明、输入参数、报文示例、返回参数、失败原因与重试处理」小节。接口说明用一两句话写调用时机，再用「项目／说明」两列表列出调用方、接收方、方法、路径及已知的媒体类型和鉴权。输入、返回分别给字段表，嵌套节点在表题标出完整路径，每个节点单独列表。失败原因与调用方动作逐行对应。有参照样板时优先沿用其小节、表头和顺序。多个接口先给可定位到正文的索引，公共请求头和报文外层集中定义，单个接口就地列出实际业务返回字段。更新已有 Markdown 时就地维护，联动更新受影响的字段、示例及上下游引用。

- **请求。** 按路径、查询、请求头、请求体等实际位置列字段。写清线上字段名、中文含义、类型、必填条件、取值来源。条件必填要说清触发条件。上游返回值写到具体接口和字段路径，需要沿用的标识说明属于哪笔业务。
- **响应。** 先给可执行的成功判断，再列对端实际返回的节点。嵌套节点写完整路径，标出对象、数组和元素类型，主记录与明细分表。分别说明字段何时出现、出现时能否为 `null`。可省略、可为 `null`、空串和空数组各按实际契约写；证据不足的项目写明已知边界。
- **约束。** 在字段所在行写会影响填值或读取的限制，如长度、金额的单位和精度、日期时区、编码与中文名称的对应关系。固定值或系统字典要有实际来源。代码只接收编码时按原接口写，保留原字段名。分页写明首屏、后续请求与停止条件；撤销写明原单关联和成功后的业务后果。
- **字典和值表。** 每类单独列 Markdown 表，每个编码一行，编码与中文名称分列。保留大小写和前导零。多个字段共用的表只定义一次，字段说明统一写“详见××字典”，链接文字与字典表标题一致。例如 `drug_type_code` 写“详见药品类别字典”。有条件必填或单位限制时，同格另写该条件。只有某个选项有特殊填写条件时才加说明列。
- **示例。** 用同一笔虚构但符合业务的记录贯穿请求、响应和后续取值。请求和响应做到完整可解析。查询参数放在地址中；JSON 代码块使用合法 JSON。按真实规则核对编号、条件字段、状态和金额。只展示部分字段时显式标为节选，另提供完整报文才能称为完整调用示例。

起草时使用[可裁剪骨架](references/outline.md)。想看一份普通接口如何写到可联调，以及医保原规范的关联字段如何表达，见[写作示范](references/examples.md)。示范中的协议字段、路径和错误码只属于各自场景。

## 交付前用示例走一遍

1. 用字段表重建示例请求。逐个检查参数位置、必填条件和上游标识。用户需要完整接入时，检查公共字段是否能从同一文档或明确引用中找到。
2. 按文档给出的成功条件判断示例响应，从根节点走到主记录、每个明细和下一步取值。逐段解析 JSON，核对字段路径、类型、枚举、空值、金额与数量；确认数组只在数组节点取元素。
3. 按已确认的失败分支读取错误信息。若结果未知或规范未定义重复提交行为，把这个具体限制写在对应操作旁。删除空章节、脚手架提示和重复公共字段。
